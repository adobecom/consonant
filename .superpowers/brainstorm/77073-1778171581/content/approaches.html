Three Architectural Approaches

All three are Chrome Extensions. The difference is how the center browser and Claude integration work.

A

Extension Tab + Webview Recommended

The extension opens a dedicated full-screen tab (chrome-extension://[id]/app.html). Center panel is a <webview> — a real embedded browser that handles auth, cookies, and DOM natively. Left and right rails are regular HTML inside the extension tab.

Pros

  • Exact 3-column layout you described
  • Real browser in center — auth just works
  • Claude can inject scripts into webview to read full DOM
  • Clean separation: app shell vs. browsed content
  • No interference with other browser tabs

Cons

  • Webview lives in a separate context — some browser devtools quirks
  • Slightly more boilerplate to wire up webview ↔ extension messaging
B

Side Panel + Content Script Injection

Claude chat lives in Chrome's native Side Panel (right side). A content script injects the left rail directly into whichever page you're on. The "center" is the real page — no webview needed, because you're already on the page.

Pros

  • Works on any tab without switching contexts
  • Native Chrome side panel UX
  • Direct DOM access with no webview messaging layer

Cons

  • Left rail injection can break page layouts
  • No URL bar — you just browse normally and activate the extension
  • Less controlled — page CSP can block content scripts
  • Not the clean 3-column dashboard feel you showed in the reference
C

Extension Tab + Local Proxy Server

Instead of a webview, a lightweight local Node.js proxy server fetches and rewrites pages, then serves them into the extension tab via an iframe. The proxy strips X-Frame-Options headers so any site can be embedded.

Pros

  • Iframe is simpler to work with than webview
  • Proxy can pre-process pages (inject scripts, rewrite URLs)

Cons

  • Requires running a local Node.js server (extra setup burden)
  • Auth is painful — session cookies don't transfer to the proxy
  • Password-protected pages break badly
  • Team members all need the proxy running
Recommendation: Option A

The webview approach is the only one that gives you the exact layout you described, handles auth on password-protected pages natively, and doesn't require any extra servers. Option B is simpler but doesn't match your reference design. Option C adds complexity with worse auth support.
